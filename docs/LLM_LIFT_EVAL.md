# LLM lift eval

This eval measures how much Lacuna's cited-answer path (the evidence ask)
improves answers compared with asking the same model the same question without
retrieval. Primary metrics are deterministic, so there is no LLM judge.

Status: the harness, frozen set, scorers, and CI gate are built. No live run has
happened yet, because no inference credential was available where the harness
was built. Every model-quality number below is a placeholder until a live run
produces measured numbers.

## Eval set

`src/lib/ai/evals/fixtures/lift-eval-set.v1.json` is generated by
`npm run eval:lift:set` (`scripts/build-lift-eval-set.ts`) from
`getVerifiedDataset()` in static mode (`src/data/dataset.verified.json`). Gold
values are copied from dataset fields. Nothing is typed by hand.

- Version: `lift-eval-set.v1`
- Items: 160. 115 answerable, 45 should-abstain (28%)
- `itemsSha256`:
  `67ec3e97e31ca82152a7a1968c89087f7eca0b19ba771646b1ea1cde6cfc107c` (sha256 of
  the canonical JSON of the item list)

| Template                   | Type           | Count | Gold                               |
| -------------------------- | -------------- | ----: | ---------------------------------- |
| `deal_value`               | answerable     |    50 | `dealValue` (USD millions)         |
| `announced_date`           | answerable     |    25 | `announcedDate`                    |
| `acquirer`                 | answerable     |    25 | `acquirer`                         |
| `founded_year`             | answerable     |    15 | company `founded`                  |
| `undisclosed_deal_value`   | should-abstain |     9 | `dealValue` is null                |
| `pending_close_date`       | should-abstain |     5 | `closedDate` is null               |
| `undisclosed_founded_year` | should-abstain |     6 | company `founded` is null          |
| `out_of_scope_revenue`     | should-abstain |    15 | the dataset has no revenue field   |
| `out_of_scope_headcount`   | should-abstain |    10 | the dataset has no headcount field |

Deal values whose notes say they are estimated or not officially disclosed are
left out of `deal_value`, so gold values are disclosed figures only. Items are
picked by sha256 ordering of record ids, so selection is stable and does not
depend on file order.

Each item has `id`, `question`, `type`, `template`, `gold` (normalized value and
kind), `goldRecordIds` (dataset ids), and `goldPassageIds` (the passage that
must be cited).

`npm run eval:lift:check` fails if the item hash changes or if any gold value no
longer matches the dataset. Change the set by bumping the version, never by
editing the frozen file.

## Corpus

The production evidence corpus covers CMS reimbursement passages, so it can not
answer deal questions. `src/lib/ai/evals/lift/corpus.ts` adapts the verified
dataset into evidence passages (corpus class `verified_dataset_adapter`,
`source_verified`, lane `research_draft`):

- `vd:{dealId}:announcement`, `vd:{dealId}:value`, `vd:{dealId}:closing`
- `vd:{companyId}:profile`

There are 335 passages. Each passage ends with
`Structured record: metric M, value V` and carries a structured record with the
dataset id in `record.code`. The verifier compares numeric records within a
metric and scope to detect conflicts. Without the id, two different deals'
values would look like a conflict on one metric. A missing value is stated as
missing and recorded as null, never as zero.

Retrieval is the app's own lexical retriever (`retrieveEvidence`), top-k 5.
Retrieval recall@5 (gold passage in the retrieved set) is model-free and
measured: 1.000, 95% CI [1.000, 1.000], n=115 answerable items.

## Arms and prompts

Every cell goes through `runEvidenceAsk` in `src/lib/ai/rag/answer.ts`:
retrieval, prompt construction, structured generation, citation verification,
and the quality gate. Nothing in that path is reimplemented.

- A, `no_retrieval`: an empty corpus with a closed-book system prompt. The model
  answers from its own knowledge or abstains. It cannot cite.
- B, `retrieval`: the adapted corpus with the evidence-ask system prompt.

Prompt versions live in `src/lib/ai/evals/lift/prompts.ts`:

- `v1`: the production `EVIDENCE_RAG_SYSTEM_PROMPT`, imported rather than copied
  (label `1.0.0`), plus a matching closed-book prompt.
- `v2` (`lift-v2.0.0`): v1 plus value rules. Copy values exactly, one value per
  question, add `claim.record` from the structured line, and abstain on missing
  values.

`runEvidenceAsk` accepts an optional `prompt: { version, system }` override.
Without one it behaves exactly as before.

## Metrics

All metrics are proportions with bootstrap 95% CIs (percentile, 2,000 resamples,
seed `20261115`). Lift is B minus A with a paired bootstrap over the same items.

| Metric                 | Denominator               | Counts as a success                                                                       |
| ---------------------- | ------------------------- | ----------------------------------------------------------------------------------------- |
| Answer accuracy        | answerable items          | not abstained and the gold value appears (money within 0.5%, exact date/year/entity)      |
| Citation correctness   | answered answerable items | cited ids are a subset of retrieved ids and include a gold passage id                     |
| Unsupported-claim rate | answered items            | a money, date, or year in the answer is absent from every cited passage (lower is better) |
| Abstention rate        | should-abstain items      | disposition is `abstain`                                                                  |
| False-abstention rate  | answerable items          | disposition is `abstain` (lower is better)                                                |

Values that the question itself supplies, such as the as-of date, do not count
as claims. A closed-book answer cites nothing, so any value it asserts counts as
unsupported. Provider errors are recorded as errors and scored as abstentions.
The harness never fills in an answer.

## Running it

```bash
npm run eval:lift:set                 # regenerate set (only when bumping version)
npm run eval:lift:check               # hash + gold drift check
npx vitest run __tests__/lib/ai/lift  # scorer tests

# Live: one pass per arm x prompt (4 cells x 160 items), temperature 0.
# Needs AI_GATEWAY_API_KEY or OPENAI_API_KEY (see docs/INFERENCE.md).
npm run eval:lift -- --live --record eval-artifacts/lift-responses.jsonl \
  --write eval-artifacts/lift-report.json --markdown eval-artifacts/lift-report.md --gate

# Replay: score recorded responses with no provider calls.
npm run eval:lift -- --replay eval-artifacts/lift-responses.jsonl --gate
```

Live mode prints only whether each credential name is set, never its value.

Live mode has two HTTP transports for the same call path (`runEvidenceAsk` ->
`generateEvidenceDraftWithInference`):

- `--transport curl`, the default when `HTTPS_PROXY` is set. It installs a
  gateway provider backed by a curl subprocess as the AI SDK default provider
  (`globalThis.AI_SDK_DEFAULT_PROVIDER`), so string model ids on the gateway
  path go through curl. Node's fetch cannot get through some credential proxies
  that inject auth, but curl can. Headers reach curl through stdin config, never
  argv. The code is in `src/lib/ai/evals/lift/curlTransport.ts`. It covers only
  the AI Gateway path, and production inference never imports it.
- `--transport fetch`, the default with no proxy. It uses Node's fetch, and when
  a proxy is set it enables Node 24's env proxy support
  (`http.setGlobalProxyFromEnv()`).

With a credential proxy that injects the gateway bearer token, a placeholder key
in the environment is enough:

```bash
AI_GATEWAY_API_KEY=proxy-injected pplx credentials run <handle> -- \
  npm run eval:lift -- --live --record eval-artifacts/lift-responses.jsonl \
  --write eval-artifacts/lift-report.json --markdown eval-artifacts/lift-report.md --gate
```

`--limit N` runs only the first N items as a smoke test. It prints each response
and builds no report.

If the first 5 provider calls all fail, the run aborts and produces no results.
A report where any cell's provider error rate is above `maxErrorRate` (0.02)
gets the status `invalid_provider_errors`, and the gate rejects it, because
errors score as abstentions and would otherwise inflate the abstention rate.

Live mode logs input and output tokens per response and per cell. Without a
credential it exits 1 with a blocked message, or exits 0 with
`--skip-if-unconfigured`.

The unit tests use a fake model (`__tests__/lib/ai/lift/fakeModel.ts`), which is
for unit tests only. Fake records carry `fake: true`, and `buildLiftReport`
rejects them unless a test passes `allowFake`. An oracle generator in the same
file shows that a perfect answer gets perfect scores through the real verifier,
so the app path does not cap the retrieval arm.

## CI gate

`.github/workflows/llm-lift-eval.yml` (`contents: read`):

- `lift-offline` always runs the scorer tests and the frozen-set check.
- `lift-live` checks for `AI_GATEWAY_API_KEY` or `OPENAI_API_KEY` in a step,
  following the same pattern as `datadog-synthetics.yml`. With no secret it logs
  a skip and succeeds. With a secret it runs the live eval and fails if any
  gated retrieval cell (`v1`) falls below the floors in
  `lift-gate.thresholds.json`, drops more than `maxDropVsBaseline` (0.05) vs
  `lift-baseline.report.json`, or has an error rate above 0.02.

The floors (accuracy 0.5, citation correctness 0.8, abstention 0.7) are policy
choices made before any run. They are not measurements. The committed baseline
has status `pending_live_run`, so the regression check is skipped until a
measured report replaces it:

```bash
npm run eval:lift -- --replay eval-artifacts/lift-responses.jsonl \
  --write src/lib/ai/evals/fixtures/lift-baseline.report.json
```

Recalibrate the floors once that baseline exists.
